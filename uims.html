UIMS — Universal Information Management System

A multi-tenant information platform for institutions that need to manage people, cameras, access events, and compliance in one system. Built as my final-year project and extended well past the coursework requirements.

Request a demo Contact

The problem

Institutions run many small systems side by side: an access-control spreadsheet, a visitor logbook, a paper-based incident register, a separate HR system. None of them talk to each other. When someone needs to know "who was in the building at 3pm," or "did this person finish their compliance training," the answer comes from three people and four files.

UIMS consolidates these into one place. Every record belongs to a tenant — a single institution. Data never crosses tenants, even by accident. That isolation is not a feature bolted on; it is enforced at the database level.

Architecture

Backend

Python 3.11 + FastAPI. SQLAlchemy for ORM. Alembic for migrations. Pydantic for request validation.

Database

PostgreSQL 16. Row-Level Security enforced by the database, not by Python. Every request opens a session scoped to a single tenant. Cross-tenant reads require an explicit bypass context that is audited.

Vision service

C++ executable. Facial recognition and license-plate reading via ONNX runtime. Streams events back to the backend over HTTPS. Windows-native today; POSIX port in progress.

Billing (external)

Separate Flask service that owns tenant plan state and invoice records. Syncs to UIMS via a signed webhook. Fail-open by design: if billing is unreachable, tenants keep working and stale data is flagged.

What it does

  • Multi-tenant isolation. Postgres RLS with a non-bypass application role. Every policy verified by CI on every commit.
  • Face recognition access events. A C++ pipeline matches faces against enrolled records; the backend records the event, links it to a person, and notifies configured channels.
  • License plate recognition. Same pipeline, separate model. Entry and exit events for vehicles; contract test suite locked in even though the producer is deferred.
  • Attendance & visitors. Per-tenant attendance logs, visitor check-in/out, and search across both.
  • Compliance & DSAR. Data Subject Access Requests and erasure, handled transactionally across eleven foreign keys tied to a person record.
  • Billing, kept separate. Tenant plans, invoices, and payments are owned by a dedicated service, not folded into the app. That separation keeps the money-handling code auditable and easier to reason about.

What I learned building it

Row-level security is not optional. An early CI run caught that our application role had BYPASSRLS silently set — every policy looked like it was working and was actually inert. The fix was to have CI create the role as NOSUPERUSER NOBYPASSRLS from the start and verify the policy still runs.

Two systems with two databases will disagree about time. A billing service and UIMS both stored datetime columns, but one was timestamp with time zone and the other timestamp without time zone. Same wall clock, three hours apart as instants. Fixing it required a migration on both sides plus a change in how every datetime is constructed. Worth doing early; expensive to do later.

Gap-free numbering is not a Postgres sequence. Sequences do not roll back. If an invoice insert fails after the sequence advances, the number is consumed and the sequence has a gap — which is not acceptable for tax-compliant invoicing. The replacement is an atomic counter row that increments inside the same transaction as the invoice insert.

Status

UIMS is under active development. The backend and RLS layer are production-shaped; the vision service runs on Windows and is being ported to macOS and Linux. Roughly 180 automated tests pass locally and in CI on every commit. Billing and admin tooling live in a separate service.
